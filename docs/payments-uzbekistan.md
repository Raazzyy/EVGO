## 1. Выбор провайдера и порядок подключения

| Провайдер | Доля рынка | Сложность интеграции | Когда подключать |
|---|---|---|---|
| **Payme** (Paycom) | Самый распространённый | Средняя — обратная логика, они вызывают нас | Первым |
| **Click** | Сопоставимая | Низкая — два эндпоинта, подпись MD5 | Вторым |
| **Uzum Bank** | Растёт | ⚠ уточнить | Третьим, если будет спрос |

**Правило: подключать строго по одному.** Каждый провайдер — это договор,
тестирование в песочнице и отдельный цикл приёмки. Попытка сделать сразу двух
параллельно почти гарантированно даёт полусырые обе интеграции.

**Начинать с Payme,** несмотря на более сложную модель: у него шире охват, и
его схема (мы поднимаем эндпоинт, они его вызывают) заставляет сразу правильно
спроектировать состояния транзакций. После Payme добавить Click — он ложится на
готовую модель почти без изменений.

## 2. Общие правила работы с деньгами

Эти четыре правила не обсуждаются. Нарушение любого из них рано или поздно даёт
расхождение баланса, которое невозможно разобрать постфактум.

### 2.1. Деньги — только целые числа

Тип `real` (число с плавающей точкой), который сейчас используется в
`sessions.cost` и `users.total_spent`, **для денег не подходит**: `0.1 + 0.2`
в нём не равно `0.3`, и на тысячах операций копейки расходятся.

**Как правильно:** хранить в тийинах (1 сум = 100 тийин) в `bigint`. Payme и
так работает в тийинах, так что конвертации на границе почти не будет.

```ts
// lib/db/src/schema/wallets.ts
amount_tiyin: bigint("amount_tiyin", { mode: "bigint" }).notNull(),
```

Форматирование в сумы — только на выводе, в одном общем хелпере.

### 2.2. Двойная запись, а не «поле баланса»

Баланс — это **не** число, которое мы увеличиваем и уменьшаем. Баланс — это
сумма неизменяемых записей в журнале транзакций.

Почему: если платёж упал посреди операции, при подходе «просто поле» невозможно
понять, применилось изменение или нет. При журнале — видно каждый шаг.

Поле `wallets.balance_tiyin` всё-таки держим, но как **кэш** для быстрого
чтения, который пересчитывается в той же транзакции базы, что и вставка записи
в журнал. Раз в сутки — сверка: сумма журнала должна совпадать с кэшем, иначе
алерт.

### 2.3. Идемпотентность

Платёжные системы **повторяют запрос**, если не получили ответ вовремя. Payme
это делает явно и документированно. Повторный вызов с тем же идентификатором
обязан вернуть **тот же результат**, а не создать вторую транзакцию и не
списать дважды.

Реализация: `provider_transaction_id` с ограничением `UNIQUE`, и любая
обработка начинается с поиска по нему.

### 2.4. Блокировка строки кошелька

Все операции с балансом — внутри транзакции базы с `SELECT … FOR UPDATE` на
строке кошелька. Без этого две одновременные зарядки одного пользователя могут
обе пройти проверку «баланса хватает» и увести его в минус.

```ts
await db.transaction(async (tx) => {
  const [w] = await tx.select().from(walletsTable)
    .where(eq(walletsTable.user_id, userId))
    .for("update");            // ← блокировка до конца транзакции
  if (w.balance_tiyin < amount) throw new InsufficientFunds();
  // … вставка в журнал + обновление кэша баланса
});
```

## 3. Модель данных

```sql
-- Кошелёк: один на пользователя
wallets(
  id             serial primary key,
  user_id        text not null unique,
  balance_tiyin  bigint not null default 0,     -- кэш, источник правды — журнал
  currency       text not null default 'UZS',
  is_blocked     boolean not null default false,
  created_at     timestamptz not null default now(),
  updated_at     timestamptz not null default now()
);

-- Журнал: неизменяемые записи, источник правды по балансу
wallet_transactions(
  id               bigserial primary key,
  wallet_id        integer not null references wallets(id),
  type             text not null,           -- topup | charge | hold | hold_release
                                            -- | refund | bonus | correction
  amount_tiyin     bigint not null,         -- >0 приход, <0 расход
  balance_after    bigint not null,         -- баланс после операции, для сверки
  reference_type   text,                    -- session | topup | manual
  reference_id     text,
  payment_id       bigint references payment_transactions(id),
  idempotency_key  text not null unique,
  comment          text,
  created_at       timestamptz not null default now()
);

-- Платежи от внешних провайдеров
payment_transactions(
  id                       bigserial primary key,
  user_id                  text not null,
  provider                 text not null,      -- payme | click | uzum
  provider_transaction_id  text,               -- id транзакции на их стороне
  amount_tiyin             bigint not null,
  state                    integer not null default 0,
  -- 0 создан счёт, 1 транзакция создана, 2 проведена,
  -- -1 отменена до проведения, -2 отменена после проведения
  cancel_reason            integer,
  create_time              bigint,             -- их таймстемпы, миллисекунды
  perform_time             bigint,
  cancel_time              bigint,
  raw_payload              jsonb,              -- сырой запрос, для разбора споров
  created_at               timestamptz not null default now(),
  updated_at               timestamptz not null default now(),
  unique (provider, provider_transaction_id)
);

-- Блокировка средств на время зарядки
wallet_holds(
  id            bigserial primary key,
  wallet_id     integer not null references wallets(id),
  session_id    integer not null,
  amount_tiyin  bigint not null,
  status        text not null default 'active',  -- active | captured | released
  expires_at    timestamptz not null,
  created_at    timestamptz not null default now()
);
```

**Почему `state` в `payment_transactions` числовой и совпадает с Payme:** чтобы
не переводить их состояния в свои и обратно. Click ложится на ту же шкалу:
prepare → 1, complete с `error=0` → 2, complete с ошибкой → -1.

### 3.1. Сценарий блокировки средств

1. Пользователь жмёт «Зарядиться». Считаем максимальную сумму: мощность
   коннектора × максимальное время × цену. Проверяем, что баланса хватает
2. Создаём `wallet_holds` со статусом `active`, баланс **не трогаем**
3. Доступный баланс = `balance_tiyin` − сумма активных холдов
4. Зарядка закончилась, оператор прислал факт: списываем реальную сумму
   (запись `charge` в журнале), холд переводим в `captured`
5. Если зарядка не началась за 15 минут — холд `released` автоматически

Без холдов человек с нулевым балансом сможет начать зарядку.

## 4. Payme Merchant API

### 4.1. Как это устроено

**Главное отличие от привычной схемы:** не мы вызываем Payme, а **Payme вызывает
нас**. Мы поднимаем один HTTP-эндпоинт, который принимает JSON-RPC 2.0 запросы.

```
POST /api/payments/payme
Content-Type: application/json
Authorization: Basic base64("Paycom:<KEY>")
```

- **Авторизация:** HTTP Basic. Логин всегда `Paycom`, пароль — 36-символьный
  ключ кассы из личного кабинета мерчанта
- **IP-адреса Payme:** `185.234.113.1` – `185.234.113.15`. Разумно добавить
  проверку по этому списку в дополнение к Basic-авторизации
- **Только POST.** На любой другой метод — ошибка `-32300`
- **Суммы в тийинах** (целое положительное число)
- **Время** — целое из 13 цифр, миллисекунды с 1 января 1970 UTC

Формат запроса:

```json
{ "jsonrpc": "2.0", "id": 1234, "method": "CheckPerformTransaction",
  "params": { "amount": 500000, "account": { "payment_id": "42" } } }
```

Формат успешного ответа:

```json
{ "jsonrpc": "2.0", "id": 1234, "result": { "allow": true } }
```

Формат ответа с ошибкой:

```json
{ "jsonrpc": "2.0", "id": 1234,
  "error": { "code": -31050, "message": { "ru": "Счёт не найден",
             "uz": "Hisob topilmadi", "en": "Account not found" },
             "data": "payment_id" } }
```

### 4.2. Методы

| Метод | Назначение |
|---|---|
| `CheckPerformTransaction` | Проверка возможности создания транзакции |
| `CreateTransaction` | Создание транзакции |
| `PerformTransaction` | Проведение транзакции |
| `CancelTransaction` | Отмена транзакции |
| `CheckTransaction` | Проверка состояния транзакции |
| `GetStatement` | Выписка по транзакциям за период |
| `SetFiscalData` | Передача фискальных данных чека |

Параметры и ответы:

```
CheckPerformTransaction
  params: { amount, account }
  result: { allow: true }
  Проверяем: счёт существует, сумма совпадает, заказ не оплачен

CreateTransaction
  params: { id, time, amount, account }
  result: { create_time, transaction, state: 1 }
  id — идентификатор транзакции на стороне Payme, 24 символа
  transaction — наш внутренний id, строкой

PerformTransaction
  params: { id }
  result: { transaction, perform_time, state: 2 }
  Здесь и только здесь зачисляем деньги на баланс

CancelTransaction
  params: { id, reason }
  result: { transaction, cancel_time, state: -1 | -2 }

CheckTransaction
  params: { id }
  result: { create_time, perform_time, cancel_time, transaction, state, reason }

GetStatement
  params: { from, to }
  result: { transactions: [ … ] }
```

### 4.3. Состояния и причины отмены

| `state` | Значение |
|---|---|
| `1` | Транзакция создана, ожидает подтверждения |
| `2` | Транзакция успешно завершена |
| `-1` | Отменена (была в состоянии 1) |
| `-2` | Отменена после завершения (была в состоянии 2) |

| `reason` | Причина отмены |
|---|---|
| `1` | Один или несколько получателей не найдены или неактивны |
| `2` | Ошибка при дебетовой операции в процессинговом центре |
| `3` | Ошибка выполнения транзакции |
| `4` | Отмена по таймауту |
| `5` | Возврат денег |
| `10` | Неизвестная ошибка |

**Таймаут: 12 часов** — 43 200 000 миллисекунд с момента создания транзакции в
Payme. После этого транзакция переходит в `-1` с причиной `4`. Наш код обязан
сам отменять просроченные транзакции, а не ждать вызова от Payme.

### 4.4. Коды ошибок

**Общие ошибки протокола:**

| Код | Когда возвращать |
|---|---|
| `-32300` | Метод запроса не POST |
| `-32700` | Ошибка парсинга JSON |
| `-32600` | Отсутствуют обязательные поля или неверные типы данных |
| `-32601` | Запрашиваемый метод не найден |
| `-32504` | Недостаточно привилегий (провал авторизации) |
| `-32400` | Внутренняя системная ошибка |

**Ошибки бизнес-логики:**

| Код | Когда возвращать |
|---|---|
| `-31001` | Неверная сумма — не совпадает с суммой счёта |
| `-31003` | Транзакция не найдена |
| `-31007` | Невозможно отменить — услуга уже оказана |
| `-31008` | Невозможно выполнить операцию — состояние транзакции не позволяет |
| `-31050` … `-31099` | Ошибки в поле `account`: счёт не найден, пользователь не найден и т. п. |

Для диапазона `-31050…-31099` поле `message` **обязано быть локализованным
объектом** с ключами `ru`, `uz`, `en`, а `data` содержит имя проблемного
подполя `account`.

### 4.5. Как это ложится на наш кошелёк

Пополнение баланса оформляем как **счёт**: заранее создаём запись в
`payment_transactions` с фиксированной суммой, и её id передаём в `account`.
Так `CheckPerformTransaction` может проверить сумму — при схеме «лицевой счёт с
произвольной суммой» проверять нечего.

```
1. Пользователь в приложении выбирает сумму пополнения
2. POST /api/wallet/topup { amount_tiyin, provider: "payme" }
   → создаём payment_transactions (state=0)
   → возвращаем ссылку на форму оплаты Payme
3. Пользователь платит в приложении Payme
4. Payme → CheckPerformTransaction  { account: { payment_id } }
   Проверяем: запись есть, state=0, сумма совпадает → { allow: true }
5. Payme → CreateTransaction
   Записываем provider_transaction_id, state=1 → { state: 1, transaction }
6. Payme → PerformTransaction
   ⚠ ТОЛЬКО ЗДЕСЬ зачисляем деньги:
     - вставляем wallet_transactions type='topup'
     - обновляем кэш баланса
     - payment_transactions.state=2
   Всё это в одной транзакции базы
7. Готово. Приложение узнаёт о зачислении по push или опросу
```

Ссылка на форму оплаты — GET на `https://checkout.paycom.uz/` с параметрами
(идентификатор кассы, поля `account`, сумма, адрес возврата), закодированными
в base64. **⚠ уточнить** точный набор и порядок параметров в разделе
«Инициализация платежей» документации — их официальная страница отдаётся
скриптом и не читается автоматически.

### 4.6. Песочница

- Тестовый сервер: **`https://test.paycom.uz`**
- Продакшен-форма оплаты: **`https://checkout.paycom.uz`**
- В кабинете мерчанта создаётся веб-касса, выдаются два ключа: рабочий и
  `TEST_KEY` для песочницы
- Перед подключением мерчант проходит две фазы приёмки:
  1. Создание и отмена **неподтверждённой** транзакции — проверяются
     авторизация, валидация суммы, существование счёта
  2. Создание, подтверждение и отмена **подтверждённой** транзакции — полный
     цикл

Пройти песочницу нужно **до** запроса на боевое подключение.

## 5. Click SHOP API

### 5.1. Как это устроено

Схема та же — Click вызывает нас, — но проще: **два эндпоинта** вместо семи
методов, и вместо Basic-авторизации подпись MD5.

```
POST /api/payments/click/prepare     (action = 0)
POST /api/payments/click/complete    (action = 1)
Content-Type: application/x-www-form-urlencoded
```

Адреса Prepare URL и Complete URL указываются в кабинете на `merchant.click.uz`.

### 5.2. Параметры запроса

| Параметр | Описание |
|---|---|
| `click_trans_id` | Идентификатор транзакции в системе Click |
| `service_id` | Идентификатор сервиса (наш, из кабинета) |
| `click_paydoc_id` | Номер платёжного документа |
| `merchant_trans_id` | Наш идентификатор заказа |
| `merchant_prepare_id` | Наш id из ответа на Prepare. **Только в Complete** |
| `amount` | Сумма в сумах, дробная строкой |
| `action` | `0` — Prepare, `1` — Complete |
| `error` | Код ошибки со стороны Click, `0` — успех |
| `error_note` | Текст ошибки |
| `sign_time` | Время в формате `YYYY-MM-DD HH:mm:ss` |
| `sign_string` | MD5-подпись запроса |

### 5.3. Формула подписи

Проверено по исходникам SDK. Конкатенация без разделителей, затем MD5:

```
Prepare  (action = 0):
  md5( click_trans_id + service_id + SECRET_KEY + merchant_trans_id
       + amount + action + sign_time )

Complete (action = 1):
  md5( click_trans_id + service_id + SECRET_KEY + merchant_trans_id
       + merchant_prepare_id + amount + action + sign_time )
```

Разница только в одном поле: в Complete между `merchant_trans_id` и `amount`
добавляется `merchant_prepare_id`. В Prepare на его месте — пустая строка.

```ts
import { createHash } from "crypto";

function clickSignature(p: ClickRequest, secretKey: string): string {
  const parts = [
    p.click_trans_id,
    p.service_id,
    secretKey,
    p.merchant_trans_id,
    p.merchant_prepare_id ?? "",   // пусто для Prepare
    p.amount,
    p.action,
    p.sign_time,
  ];
  return createHash("md5").update(parts.join(""), "utf8").digest("hex");
}
```

Сравнивать результат с `sign_string` нужно **побайтово и с постоянным
временем** (`crypto.timingSafeEqual`), а не обычным `===`.

### 5.4. Коды ошибок

Проверено по официальной библиотеке `click-llc/click-integration-php`:

| Код | `error_note` | Когда возвращать |
|---|---|---|
| `0` | Success | Успех |
| `-1` | SIGN CHECK FAILED! | Подпись не совпала |
| `-2` | Incorrect parameter amount | Сумма не совпадает с заказом |
| `-3` | Action not found | Неизвестное значение `action` |
| `-4` | Already paid | Заказ уже оплачен |
| `-5` | User does not exist | Пользователь или заказ не найден |
| `-6` | Transaction does not exist | Транзакция не найдена |
| `-8` | Error in request from click | Некорректный запрос |
| `-9` | Transaction cancelled | Транзакция отменена |

Код `-7` в библиотеке присутствует как «ошибка обновления пользователя», но
в нашем сценарии не применяется.

### 5.5. Ответы мерчанта

```json

{ "click_trans_id": 123456, "merchant_trans_id": "42",
  "merchant_prepare_id": 42, "error": 0, "error_note": "Success" }

// Complete
{ "click_trans_id": 123456, "merchant_trans_id": "42",
  "merchant_confirm_id": 42, "error": 0, "error_note": "Success" }
```

### 5.6. Как это ложится на наш кошелёк

```
1. POST /api/wallet/topup { amount_tiyin, provider: "click" }
   → payment_transactions (state=0), merchant_trans_id = его id
2. Click → Prepare
   Проверяем подпись, сумму, что заказ не оплачен
   state=1, отвечаем merchant_prepare_id
3. Click → Complete
   Проверяем подпись и что error=0
   ⚠ ТОЛЬКО ЗДЕСЬ зачисляем деньги, той же функцией, что и для Payme
   state=2
```

Функция зачисления должна быть **одна на всех провайдеров** — она принимает
`payment_transaction_id` и делает всё остальное сама. Провайдер-специфичным
остаётся только разбор запроса и проверка подлинности.

## 6. Uzum Bank

**⚠ Данных мало.** Документация на `developer.uzumbank.uz` отдаётся
JavaScript-приложением и не читается автоматически, так что спецификацию нужно
брать вручную.

Что известно:

- Есть раздел Merchant API, покрывающий онлайн-платежи, QR-платежи, привязку
  карт, возвраты, статусы и фискализацию
- Поддерживаются карты Uzum, Humo, Uzcard, Visa, Mastercard
- Подключение мерчанта — через `merchants.uzumbank.uz`

Что запросить у них при подключении:

1. Кто кого вызывает — та же схема «они вызывают нас» или обычная REST
2. Способ авторизации и подпись
3. Есть ли песочница
4. Тарифы и сроки расчётов
5. Поддерживается ли возврат (refund) через API

Подключать третьим, после того как Payme и Click работают в бою.

## 7. SMS для входа по номеру телефона

Относится к этапу 1, но упомянуто здесь, потому что договор оформляется в тот
же заход, что и с платёжными системами.

**Eskiz.uz** — распространённый SMS-шлюз, есть открытые SDK.

- Авторизация двухшаговая: email как логин и секретный ключ как пароль →
  получаем токен → токеном подписываем запросы на отправку. Токен нужно
  обновлять, готовые SDK делают это автоматически
- Документация опубликована в Postman (ссылка в разделе 9)
- **⚠ уточнить:** сроки регистрации имени отправителя (alphanumeric sender ID)
  и требования к тексту шаблонов. Обычно шаблоны проходят модерацию, и
  отправить произвольный текст нельзя — это влияет на формулировку кода
  подтверждения

Альтернатива — **Play Mobile**. Имеет смысл получить условия у обоих и выбрать
по цене и срокам.

**Обязательно на нашей стороне:** ограничение частоты запроса кода (не чаще
раза в минуту на номер, не больше 5 в час), иначе через нас будут слать SMS за
наш счёт.

## 8. Чек-лист перед началом реализации

**Юридическое и коммерческое** — блокирует разработку:

- [ ] Юридическое лицо в Узбекистане для договоров
- [ ] **Ответ юриста: имеем ли право хранить остаток на внутреннем балансе.**
      Если нет — вместо кошелька списание по факту с привязанной карты, и вся
      модель данных меняется
- [ ] Договор с Payme, получена тестовая касса
- [ ] Тарифы: комиссия провайдера, сроки зачисления
- [ ] Решено, кто выставляет фискальный чек — мы или оператор станции

**Техническое** — можно начинать сразу:

- [ ] Перевести денежные поля с `real` на `bigint` в тийинах
- [ ] Таблицы `wallets`, `wallet_transactions`, `payment_transactions`,
      `wallet_holds`
- [ ] Общая функция зачисления, не зависящая от провайдера
- [ ] Тесты на: двойной вызов `PerformTransaction`, отмену после проведения,
      гонку двух списаний, недостаток средств, истечение холда
- [ ] Логирование всех запросов провайдеров в `raw_payload` — при споре это
      единственное доказательство
- [ ] Ежесуточная сверка: сумма журнала против кэша баланса, расхождение — алерт

**Без чего нельзя выкатывать в бой:**

- [ ] Пройдена песочница Payme (обе фазы)
- [ ] Проверка IP-адресов Payme в дополнение к Basic-авторизации
- [ ] Сравнение подписи Click через `timingSafeEqual`
- [ ] Отмена просроченных транзакций (12 часов) по расписанию
- [ ] Ручка в админке: посмотреть журнал кошелька пользователя и сделать
      корректировку с обязательным комментарием

## 10. Что осталось выяснить

Сведено в один список, чтобы задать вопросы одним заходом.

**У Payme:** тарифы, сроки зачисления средств, точный формат checkout-ссылки,
требования к фискализации через `SetFiscalData`, возможен ли возврат через API.

**У Click:** тарифы, есть ли песочница и как в неё попасть, порядок
подключения, поддержка возвратов.

**У Uzum:** вся техническая спецификация, схема взаимодействия, песочница,
тарифы.

**У Eskiz или Play Mobile:** сроки регистрации имени отправителя, требования к
шаблонам сообщений, цена за SMS, лимиты.

**У юриста:** форма хранения остатка пользователя, требования к фискальным
чекам, нужна ли лицензия на нашу деятельность.
