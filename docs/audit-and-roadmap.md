## 1. Резюме для директора

**Что есть сейчас.** Работающий прототип агрегатора зарядных станций: мобильное
приложение (iOS/Android/веб), админ-панель и общий backend. Карта станций
Узбекистана, фильтры, детали станции, бронирование коннектора, построение
маршрута с расчётом остановок под конкретный автомобиль, каталог из 1189
электромобилей, финансовая аналитика в админке. Визуально приложение выглядит
как готовый продукт.

**Чего нет.** Всё, что превращает прототип в бизнес:

| Блок | Статус | Почему критично |
|---|---|---|
| Регистрация и вход пользователей | **отсутствует** | Пользователь захардкожен как `user_001`. Реальных аккаунтов нет |
| Кошелёк и оплата | **заглушка** | Нельзя пополнить баланс и нельзя списать деньги за зарядку |
| Связь с зарядками партнёров | **отсутствует** | Нельзя удалённо запустить и остановить зарядку. Статусы станций проставляются вручную |
| Push-уведомления | **отсутствует** | Пользователь не узнает, что зарядка закончилась |
| Узбекский язык | **отсутствует** | Интерфейс только на русском |
| Лендинг | **отсутствует** | Нечего показать партнёрам и рекламе |

**Главный вывод.** Приложение сейчас — качественная витрина. Три вещи отделяют
его от продукта, на котором можно зарабатывать, и делать их нужно строго в этом
порядке:

1. **Аккаунты** (вход по номеру телефона) — без этого невозможно ничего
   персонального: ни кошелёк, ни история, ни уведомления
2. **Кошелёк** (пополнение через Payme/Click/Uzum, списание за сессию) — это и
   есть монетизация
3. **Интеграция с операторами** (TOKBOR, MEGAWATT, KWATT, ENERGO) по протоколу
   OCPI — без неё «зарядка через партнёров» физически невозможна, а живые
   статусы станций придётся вечно проставлять руками

Пункты 1 и 2 — чисто наша разработка, зависят только от нас. Пункт 3 требует
**договорённостей с операторами и выдачи нам API-доступа** — это не программная
задача, а коммерческая, и начинать переговоры нужно уже сейчас, параллельно с
разработкой.

**Оценка по срокам** (один разработчик, полный рабочий день):

| Этап | Оценка |
|---|---|
| Этап 0 — безопасность и гигиена | 2–3 дня |
| Этап 1 — аккаунты и авторизация | 5–7 дней |
| Этап 2 — кошелёк и платежи | 10–14 дней |
| Этап 3 — узбекский язык, push, полировка | 7–10 дней |
| Этап 4 — лендинг | 3–4 дня |
| Этап 5 — OCPI с одним оператором | 10–15 дней |
| Этап 6 — публикация в App Store и Google Play | 5–7 дней + ожидание модерации |

Итого до полноценного релиза: **примерно 2–2,5 месяца** работы, плюс время на
переговоры с операторами и на модерацию в сторах (которая от нас не зависит).

## 2. Что уже сделано

Проект — монорепозиторий на pnpm workspaces. 18 таблиц базы данных, 17 групп
API-маршрутов.

### 2.1. Архитектура

```
artifacts/
  api-server/    Express 5 + Drizzle ORM + PostgreSQL — общий backend
  mobile/        Expo Router — iOS, Android и веб из одного кода
  admin/         Vite + React + shadcn/ui — админ-панель
  mockup-sandbox/ песочница для прототипирования интерфейсов
lib/
  db/            схема базы данных (источник правды)
  api-spec/      OpenAPI-спецификация
  api-zod/       схемы валидации, генерируются из OpenAPI через Orval
  api-client-react/ React-хуки для запросов, тоже генерируются
```

Решение хорошее: типы и клиент генерируются из одной спецификации, поэтому
backend и приложение не расходятся между собой.

### 2.2. Реализованная функциональность

**Мобильное приложение**

- Карта станций: на телефоне Google Maps через `react-native-maps`, в браузере
  Leaflet. Пины окрашены по статусу, есть кластеризация
- Переключатель «Карта / Список», быстрые фильтры «Все / Свободные / Мои машины»
- Панель фильтров: тип коннектора, мощность, цена, оператор, удобства
- Блок «Рекомендуем» с пометкой «Реклама» отделён от списка «Рядом с вами» —
  промо-станции не подмешиваются к обычной выдаче
- Детали станции с адаптивной сеткой коннекторов (1 колонка при одном
  коннекторе, 2 при 2–6, 3 компактных при 7 и более)
- **Бронирование коннектора** с автоматическим освобождением по таймауту —
  реализовано полноценно (`artifacts/api-server/src/routes/connectors.ts`)
- Активная сессия зарядки: круговой индикатор с плавной анимацией
- Маршруты: геокодирование через Яндекс, построение через Google Directions,
  **собственный расчёт точек остановки** исходя из запаса хода выбранного
  автомобиля. Это самая ценная техническая часть — картографические API такого
  не дают
- Пошаговая навигация с инструкциями на русском
- «Мои автомобили»: поиск по каталогу из 1189 электромобилей, поиск понимает
  кириллицу и опечатки (61 алиас: «тесла» → tesla, «бид» → byd), есть нечёткий
  поиск через расширение PostgreSQL `pg_trgm`
- Избранное, история сессий, чеки, экран уведомлений, поддержка

**Админ-панель**

Дашборд, станции, операторы, сессии, пользователи, автомобили, промо-акции,
баннеры, поддержка и раздел «Финансы» — со сравнением двух периодов,
дельтами в процентах и выгрузкой в XLSX.

**Данные**

- Импорт станций из OpenChargeMap по фильтру `countrycode=UZ`
  (`artifacts/api-server/src/scripts/import-ocm.ts:79`)
- Еженедельная синхронизация каталога электромобилей из открытого датасета
  OpenEV
- Живой поиск автомобилей через API Ninjas с кэшированием в свою базу

## 3. Критические проблемы

Пронумерованы по приоритету. P0 — обязательно до любого публичного запуска.

### P0-1. Аутентификации пользователей нет вообще

**Где:** `artifacts/mobile/contexts/AppContext.tsx:3`

```ts
const DEMO_USER_ID = 'user_001';
const DEMO_USER_NAME = 'Akbar Pulatov';
```

Приложение работает от имени одного захардкоженного пользователя. Экрана входа
нет. В таблице `users` нет ни пароля, ни подтверждения телефона.

**Следствие на стороне API:** запросы никем не проверяются. Например,
`GET /api/payment-methods` (`artifacts/api-server/src/routes/payment_methods.ts:11`)
возвращает **платёжные методы всех пользователей сразу**, без фильтра по
`user_id`. То же по смыслу касается сессий, избранного и автомобилей — параметр
`user_id` приходит от клиента и принимается на веру, то есть любой может
подставить чужой.

**Что делать:** вход по номеру телефона с подтверждением SMS-кодом (в
Узбекистане это стандарт, email почти не используется). Детали в разделе 5.1.

### P0-2. Кошелька и реальной оплаты нет

**Где:** `artifacts/api-server/src/routes/sessions.ts:129`

```ts
// POST /sessions/:id/pay — mock payment confirmation
```

Метод просто ставит сессии статус `completed` и считает стоимость. Деньги нигде
не двигаются.

В таблице `users` нет поля баланса. Таблицы транзакций нет вообще. Таблица
`payment_methods` хранит только `type` и `last_four` — то есть «Visa •••• 4242»
как текст, без привязки к реальной карте.

**Следствие:** описанный сценарий «пополнить баланс и заряжаться у партнёров»
на сегодня не реализован ни на один процент.

**Что делать:** раздел 5.2.

### P0-3. Интеграции с операторами нет

**Где:** `lib/db/src/schema/operators.ts`

Поля под интеграцию заложены — `api_type` (принимает `ocpi`/`ocpp`/`custom`),
`api_endpoint`, `api_credentials`, `default_margin_pct`. Но **ни одного клиента
к этим API в коде нет.** Статус станции (свободна/занята) меняется вручную
тумблером в админке — в спецификации это честно названо временным решением.

**Следствие:** три вещи невозможны:

1. Показывать **реальную** занятость станций
2. Запустить зарядку из приложения (remote start)
3. Получить от оператора факт зарядки и сумму, чтобы списать деньги

**Что делать:** раздел 5.3. Требует коммерческих договорённостей.

### P0-4. Дыры в безопасности

| Проблема | Файл | Суть |
|---|---|---|
| Админ-токен не истекает | `artifacts/api-server/src/routes/admin.ts:19` | В токен пишется `Date.now()`, но `verifyToken` время **не проверяет**. Однажды выданный токен действует вечно |
| Резервный секрет в коде | `artifacts/api-server/src/routes/admin.ts:11` | Если переменная `ADMIN_JWT_SECRET` не задана, используется `"ion_admin_fallback_dev_secret_change_me"`. Токены становятся подделываемыми кем угодно |
| Ключи операторов открытым текстом | `lib/db/src/schema/operators.ts` | Поле `api_credentials` — обычный `text`. В коде помечено «plaintext MVP» |
| API-ключи в истории git | `attached_assets/*.txt` | Ключи Google Maps, Яндекс и API Ninjas лежат в четырёх текстовых файлах, попавших в репозиторий |

**Что делать:** раздел 5.0. Это два-три дня работы и должно быть сделано первым,
потому что дальше цена ошибки только растёт.

### P0-5. Push-уведомления не отправляются

Таблица `push_tokens` в базе есть, экран уведомлений в приложении есть, но кода
отправки через Expo Push API нет ни строки — поиск по `exp.host` и
`ExpoPushToken` по всему проекту не даёт ни одного совпадения.

**Следствие:** уведомление «зарядка завершена» приходит, только пока приложение
открыто на экране. Для сервиса зарядок это ломает основной сценарий: человек
уходит от машины и должен узнать, что она зарядилась.

## 4. Продуктовые пробелы

### P1-1. Нет узбекского языка

Тексты зашиты прямо в разметку: `'Карта'`, `'Список'`, `'Свободные'`,
`'РЯДОМ С ВАМИ'` и так далее. Библиотеки локализации в проекте нет.

Для Узбекистана нужны минимум **узбекский (латиница)** и **русский**,
желательно английский. Это не косметика: для части аудитории отсутствие
узбекского — причина не пользоваться приложением, а для государственных и
партнёрских переговоров это может быть формальным требованием.

Объём работы: подключить `i18next` + `expo-localization`, вынести примерно
300–400 строк, перевести. Отдельно — **форматирование сумм в сумах** (уже есть
`artifacts/admin/src/lib/formatUzs.ts`, надо распространить на приложение) и дат.

### P1-2. Нет лендинга

Файл `artifacts/mobile/server/templates/landing-page.html` — это служебная
заглушка Replit для веб-версии Expo, а не маркетинговая страница.

Нужна страница с: картой покрытия, объяснением «как это работает» в три шага,
ссылками на App Store и Google Play, отдельным блоком для операторов
(«подключите свои станции») и формой обратной связи. Подробнее в 5.4.

### P1-3. Каталог станций неполный и непроверенный

Сейчас единственный автоматический источник — OpenChargeMap по фильтру
«Узбекистан». Это открытая база, которую наполняют энтузиасты: покрытие
неполное, часть станций устарела, цены почти везде отсутствуют или неверны.

Чтобы заявлять «все зарядки Узбекистана», нужно:

- Свести данные OpenChargeMap с сайтами и приложениями TOKBOR, MEGAWATT,
  KWATT, ENERGO
- Провести **ручную верификацию** — как минимум по Ташкенту, желательно с
  выездом или обзвоном
- Добавить в админку признак «проверено, дата проверки, кем» и показывать
  пользователю, когда данные подтверждались в последний раз
- Дать пользователям кнопку «сообщить о неточности» — это самый дешёвый способ
  поддерживать базу в актуальном состоянии

Без этого этапа главное обещание продукта не выполняется, каким бы красивым ни
было приложение.

### P2-1. Нет тестов и CI

В проекте ноль тестов и нет ни одного workflow GitHub Actions. При текущем
размере кодовой базы (около 90 файлов приложения плюс backend) любая правка
может незаметно сломать соседнюю функцию.

Минимум: прогон `pnpm run typecheck` на каждый push и тесты на денежную логику,
когда она появится. Считать деньги без тестов нельзя.

### P2-2. Технический долг

- **`is_promoted` хранится числом 0/1, а не булевым значением.** В React Native
  запись вида `{is_promoted && ...}` при значении `0` выводит на экран текст
  «0» и роняет приложение. Уже описано в заметках проекта как известная
  ловушка — правильнее исправить тип в базе, чем помнить об этом вечно
- **`ion-ev-source.zip`** — архив исходников внутри репозитория, дублирует
  `artifacts/mobile/`. Удалить
- **`attached_assets/`** — 16 МБ скриншотов из 20 МБ репозитория. Вынести
- **`replit.md` не заполнен** — остались шаблонные заглушки вида
  «[Project name]» и «_Populate as you build_». Это файл, из которого агент
  берёт контекст о проекте, и пустой он вредит качеству дальнейшей работы

## 5. План работ по этапам

### Этап 0. Безопасность и гигиена (2–3 дня)

Делается первым, до любой новой функциональности.

1. Перевыпустить ключи Google Maps, Яндекс и API Ninjas — старые засветились в
   переписке и в git. Для Google обязательно настроить ограничения:
   Application restrictions (имя пакета Android + SHA-1, bundle ID для iOS) и
   API restrictions (только Maps SDK и Directions). Сейчас это один общий ключ
   без ограничений — при утечке по нему можно потратить наши деньги
2. Вычистить `attached_assets/` и `ion-ev-source.zip` из истории git через
   `git filter-repo`, добавить в `.gitignore`
3. Добавить проверку срока жизни админ-токена (например, 12 часов) и убрать
   резервный секрет — при отсутствии `ADMIN_JWT_SECRET` сервер должен падать
   при старте, а не работать с известным ключом
4. Зашифровать `api_credentials` операторов
5. Заполнить `replit.md` реальным описанием проекта
6. Настроить GitHub Actions: `typecheck` на каждый push

### Этап 1. Аккаунты и авторизация (5–7 дней)

**Схема входа:** номер телефона → SMS с кодом → JWT (access + refresh).

**SMS-шлюз.** В Узбекистане обычно используют **Eskiz.uz** или **Play Mobile**.
Оба требуют договора, юридического лица и регистрации отправителя (alphanumeric
sender ID). Регистрация имени отправителя занимает несколько дней — **начинать
надо заранее**, иначе этап встанет не по технической причине.

**Работы по базе:**

- В `users`: добавить `phone` как уникальное поле, `phone_verified_at`,
  `language` (uz/ru/en), убрать обязательность `email`
- Новая таблица `otp_codes`: телефон, хеш кода, срок действия, число попыток.
  Обязательно ограничение частоты запросов — иначе на нас будут отправлять SMS
  за наш счёт
- Новая таблица `refresh_tokens` с возможностью отзыва

**Работы по API:**

- `POST /api/auth/request-code`, `POST /api/auth/verify-code`,
  `POST /api/auth/refresh`, `POST /api/auth/logout`
- Middleware `requireAuth`, подставляющее `req.userId` из токена
- **Пройти по всем существующим маршрутам** и заменить `user_id` из тела и
  параметров запроса на `req.userId`. Это обязательный шаг, иначе дыра из P0-1
  остаётся открытой

**Работы по приложению:**

- Экраны: ввод телефона, ввод кода, заполнение профиля
- Хранение токенов в `expo-secure-store`, а не в обычном хранилище
- Заменить `AppContext` с демо-пользователем на реальную сессию
- Обработка выхода и протухшего токена

### Этап 2. Кошелёк и платежи (10–14 дней)

> **Подробная техническая спецификация:** [payments-uzbekistan.md](./payments-uzbekistan.md)
> — модель данных, методы Payme и Click с кодами ошибок и формулой подписи,
> чек-лист перед реализацией и список вопросов к провайдерам.

Самый ответственный этап. Здесь считаются деньги, и ошибка стоит дороже, чем
где-либо ещё.

**Правило: двойная запись.** Баланс пользователя не должен быть просто числом,
которое мы увеличиваем и уменьшаем. Нужна таблица транзакций, где каждая
операция — отдельная неизменяемая запись, а баланс считается как сумма. Иначе
при сбое посреди платежа концы не сойдутся, и разобраться постфактум будет
невозможно.

**Схема базы:**

```
wallets(id, user_id, balance_uzs, currency, created_at, updated_at)

wallet_transactions(
  id, wallet_id, type, amount_uzs, balance_after,
  reference_type, reference_id,        -- на что ссылается: сессия, пополнение
  provider, provider_transaction_id,   -- payme | click | uzum
  status,                              -- pending | completed | failed | cancelled
  idempotency_key UNIQUE,              -- защита от двойного списания
  created_at
)
-- type: topup | charge | refund | bonus | correction

payment_transactions(
  id, user_id, provider, provider_transaction_id UNIQUE,
  amount_uzs, state, raw_payload jsonb, created_at, updated_at
)
```

**Ключевые технические требования:**

- **Идемпотентность.** Платёжные системы повторяют запросы при таймауте.
  Повторный вызов с тем же идентификатором обязан вернуть прежний результат, а
  не списать второй раз
- **Блокировка средств.** При старте зарядки сумма резервируется (holds), при
  завершении списывается фактическая. Иначе человек начнёт зарядку с нулевым
  балансом
- **Все денежные операции — в транзакции базы данных** с блокировкой строки
  кошелька (`SELECT ... FOR UPDATE`)
- **Суммы хранить в целых числах** (в тийинах или в сумах без дробной части).
  `real`, который используется сейчас в `sessions.cost`, для денег
  **не подходит** — это тип с плавающей точкой, он теряет копейки

**Платёжные провайдеры Узбекистана.** Проверить актуальные условия перед
интеграцией, здесь общая картина:

| Провайдер | Модель интеграции | Комментарий |
|---|---|---|
| **Payme** (Paycom) | Merchant API на JSON-RPC. Мы реализуем эндпоинт, который они вызывают: `CheckPerformTransaction`, `CreateTransaction`, `PerformTransaction`, `CancelTransaction`, `CheckTransaction`, `GetStatement`. Авторизация — Basic с ключом мерчанта | Самый распространённый. Логика «наш сервер отвечает на их запросы» — обратная привычной |
| **Click** | SHOP API: два наших эндпоинта `Prepare` и `Complete`, подпись MD5 | Проще Payme |
| **Uzum Bank** (бывш. Apelsin) | Отдельный merchant API | Быстро растёт, стоит поддержать вторым или третьим |

Реализовывать лучше **по одному**, начиная с Payme, и только после того как он
полностью отлажен, добавлять следующего. Каждому нужен договор и юридическое
лицо.

**Юридический вопрос — вынести директору.** Хранение денег пользователей на
внутреннем балансе в большинстве юрисдикций является регулируемой
деятельностью. Обычно проблема решается тем, что средства формально остаются у
платёжной организации, а мы ведём только учёт. **До начала разработки кошелька
нужно уточнить у юриста, в какой форме мы имеем право хранить остаток
пользователя.** Это может изменить архитектуру: например, вместо баланса —
привязанная карта и списание по факту каждой зарядки.

**Работы по приложению:** экран кошелька (баланс, история), пополнение с
выбором суммы и провайдера, возврат из платёжного приложения обратно в наше,
чек по завершении сессии, обработка недостатка средств.

### Этап 3. Локализация, push и полировка (7–10 дней)

**Локализация**

- Подключить `i18next` + `react-i18next` + `expo-localization`
- Вынести все строки в `locales/uz.json`, `ru.json`, `en.json`
- Язык по умолчанию — из системных настроек телефона, с возможностью сменить в
  профиле, выбор сохраняется в поле `users.language`
- Уведомления и SMS отправлять на языке пользователя
- Формат сумм: `1 250 000 so'm` / `1 250 000 сум`

**Push-уведомления**

- Регистрация токена устройства при первом запуске, сохранение в `push_tokens`
- Отправка через Expo Push API (бесплатно, отдельный ключ не нужен)
- События: зарядка завершена, станция освободилась (для тех, кто её отслеживал
  — таблица `connector_watchers` уже есть), скидка рядом, низкий баланс,
  истекает бронь
- Для веб-версии — Web Push, требует пары VAPID-ключей
- Обязательно настройки уведомлений в профиле, иначе часть людей отключит их
  целиком на уровне системы

**Полировка интерфейса** (используем установленные скиллы `apple-design`,
`animate-expo`, `emil-design-eng`, `vercel-react-native-skills`)

- Единая дизайн-система: сейчас цвета частично зашиты в компонентах
- Анимации переходов, состояний загрузки (скелетоны вместо спиннеров),
  тактильная отдача на ключевых действиях
- Пустые состояния: что видит человек, когда рядом нет станций, нет истории,
  нет интернета
- Обработка ошибок: сейчас есть `ErrorBoundary`, но нет внятных сообщений
  пользователю
- Доступность: размеры кнопок не меньше 44 пунктов, контраст, поддержка
  крупного системного шрифта

### Этап 4. Лендинг (3–4 дня)

Отдельная страница, не часть приложения. Стек: Vite + React + Tailwind, как в
админке, чтобы не плодить технологии.

**Структура:**

1. Первый экран: название, одно предложение сути, кнопки App Store и Google
   Play, скриншот приложения
2. Живая карта покрытия — реальные станции из нашего API, а не картинка. Это
   лучшее доказательство, что сервис работает
3. «Как это работает» в три шага: найди → заряди → оплати с баланса
4. Возможности: маршруты с остановками, бронирование, каталог автомобилей
5. Блок для операторов: «подключите свои станции» + форма заявки. Отдельный
   призыв к действию, потому что это второй тип клиента
6. Частые вопросы, контакты, ссылки на политику конфиденциальности и условия
   использования — **они обязательны для публикации в сторах**

Требования: три языка, открытие быстрее секунды на мобильном интернете,
метатеги Open Graph для ссылок в Telegram.

### Этап 5. Интеграция с операторами по OCPI (10–15 дней на первого)

**Это не только программная задача.** Сначала нужны договорённости.

**Что запросить у каждого оператора** (TOKBOR, MEGAWATT, KWATT, ENERGO):

1. Поддерживают ли они OCPI, и какую версию (стандарт — 2.2.1)
2. Если нет — есть ли любой другой API, хотя бы на чтение статусов
3. Условия роуминга: комиссия, кто выставляет счёт конечному пользователю
4. Тестовый контур и учётные данные

**Если OCPI есть** — реализуем модули:

- `credentials` — рукопожатие и обмен токенами
- `locations` — станции, коннекторы и их **живые статусы**
- `commands` — `START_SESSION` и `STOP_SESSION`, то есть удалённый запуск
  зарядки. Ключевая функция
- `sessions` — активная сессия и показания
- `cdrs` — итоговый документ о зарядке, по нему списываем деньги
- `tokens` — наши пользователи в системе оператора

**Если OCPI нет** — три варианта, по убыванию предпочтительности:

1. Убедить оператора его сделать (это отраслевой стандарт, ему это полезно и с
   другими агрегаторами)
2. Написать адаптер под их собственный API
3. Оставить ручной режим: показываем станцию на карте, но зарядка и оплата — на
   стороне оператора. Мы остаёмся справочником, а не платёжным звеном

**Отдельный сценарий — свои зарядки.** Если компания ставит собственные
станции, с ними разговаривают напрямую по **OCPP 1.6J** (WebSocket от станции к
нашему серверу). Это другая по характеру задача, чем OCPI, и требует отдельной
оценки.

### Этап 6. Публикация (5–7 дней плюс модерация)

- Иконки и экраны запуска во всех размерах
- Скриншоты для сторов на трёх языках
- Описания, ключевые слова
- Политика конфиденциальности и условия использования на сайте (обязательно)
- Декларации Apple о сборе данных (App Privacy) — геолокация, платежи, контакты
- Настройка аккаунтов разработчика: Apple 99 долларов в год, Google 25 долларов
  единоразово
- Публикация Android-сборки, затем iOS

Apple проверяет от суток до недели, отказы на первой подаче — обычное дело.
Закладывать на это время в план.

## 6. Вопросы, на которые нужен ответ директора

Без них нельзя корректно спланировать этапы 2 и 5.

**По деньгам и юридической схеме**

1. Есть ли юридическое лицо в Узбекистане, на которое оформляются договоры с
   Payme/Click и SMS-шлюзом?
2. **Имеем ли мы право хранить остаток средств пользователя на внутреннем
   балансе?** Если нет — вместо кошелька делаем списание по факту с
   привязанной карты, это меняет объём работ
3. Как мы зарабатываем: наценка на киловатт-час, комиссия с оператора,
   абонентская плата, реклама промо-станций? В базе уже есть поля
   `cost_price_per_kwh` и `default_margin_pct` — то есть модель наценки
   заложена, надо подтвердить
4. Кто выставляет чек конечному пользователю — мы или оператор? От этого
   зависит вся схема фискализации

**По операторам**

5. Есть ли уже контакт или договорённость с TOKBOR, MEGAWATT, KWATT, ENERGO?
6. Готовы ли они дать API-доступ, и в какие сроки?
7. Планируем ли ставить **собственные** зарядные станции? Это другой протокол
   (OCPP) и отдельный бюджет

**По продукту**

8. Приоритет рынка: только Ташкент на старте или весь Узбекистан сразу?
9. Нужен ли узбекский язык на запуске или можно добавить второй версией?
   (рекомендация — на запуске)
10. Что делаем со станциями операторов, с которыми нет интеграции: показываем
    как справочник или прячем? (рекомендация — показывать с пометкой «оплата на
    месте», полнота карты важнее)

**По команде**

11. Кто ведёт разработку дальше и сколько человек? Оценки в разделе 1 даны на
    одного разработчика
12. Остаёмся ли на Replit или переезжаем на обычный хостинг? Для платежей
    понадобятся стабильные IP и домен, у операторов и платёжных систем часто
    требуется белый список адресов

## 7. Риски

| Риск | Вероятность | Что делать |
|---|---|---|
| Операторы не дадут API-доступ | Высокая | Начинать переговоры немедленно, параллельно разработке. Заранее продумать ценность продукта без интеграции — карта, маршруты, каталог автомобилей работают и так |
| Данные о станциях неточные, пользователь приезжает к нерабочей зарядке | Высокая | Ручная верификация по Ташкенту, кнопка «сообщить о неточности», показ даты последней проверки |
| Юридические ограничения на хранение баланса | Средняя | Выяснить **до** начала этапа 2 |
| Регистрация SMS-отправителя затянется | Средняя | Подать документы на старте этапа 0 |
| Отказ Apple при публикации | Средняя | Заложить время, подготовить материалы заранее |
| Ключи Google Maps утекут и по ним потратят бюджет | Уже произошло частично | Этап 0, пункт 1 — ограничения на ключи |

## 8. Что рекомендую делать прямо сейчас

Порядок именно такой:

1. **Этап 0 целиком** — 2–3 дня, снимает риски, ничего не блокирует
2. **Параллельно:** директор запускает переговоры с операторами и выясняет
   юридический вопрос по балансу
3. **Параллельно:** подать документы на SMS-шлюз
4. **Этап 1** — аккаунты. Без них дальше двигаться нельзя
5. **Этап 4** — лендинг. Можно делать в любой момент, даёт материал для
   переговоров с операторами и партнёрами
6. **Этап 2** — кошелёк, когда придёт ответ по юридической части
